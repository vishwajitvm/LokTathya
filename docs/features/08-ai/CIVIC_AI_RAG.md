## 1. Overview
This document specifies the grounded retrieval-augmented generation (RAG) architecture, hybrid database retrieval, prompt validation chains, and security boundaries of the Civic AI assistant in LokTathya. The Civic AI assistant acts as a natural language interface, converting user queries into grounded answers with explicit citations.

---

## 2. Problem Statement
Generic conversational AI chatbots regularly invent civic statistics, election histories, and representative portfolios. Hallucinations in a public civic database undermine trust and spread misinformation. We must restrict the Large Language Model (LLM) to verified database records and prevent it from generating arbitrary or ungrounded claims.

---

## 3. Goals
* **Deterministic Grounding**: Limit LLM responses strictly to verified database context records.
* **Citation Validation**: Ensure every claim generated by the LLM is linked to a database entity and source ID.
* **Security & Isolation**: Prevent prompt injections and SQL injection exploits.

---

## 4. Non-Goals
* Running open-ended conversations, writing creative content, or executing direct SQL statements generated by the LLM.

---

## 5. Target Users
* **Citizens**: Ask natural-language questions about local representatives, budgets, and projects.
* **Journalists**: Verify candidate disclosures and election histories using conversational search.
* **Researchers**: Quickly locate specific datasets and reports.

---

## 6. User Stories
* As a citizen, I want to ask "Who is the MP of Shillong and what projects are active?" and receive a grounded answer with citations.
* As an administrator, I want to verify that the LLM is not executing arbitrary SQL statements on the database.

---

## 7. User Journey
1. **Query**: The user types a question in the `/civic-ai` chat interface.
2. **Retrieve**: The RAG pipeline queries pgvector and PostgreSQL tables to fetch context.
3. **Inference**: The LLM processes the grounded prompt and returns an answer with citations.
4. **Inspect**: The user clicks the citations to view the source documents.

---

## 8. Functional Requirements
* **Hybrid Retrieval**: Combine PostgreSQL full-text search (FTS) with vector similarity search (pgvector) using a semantic embedding model.
* **Tool Routing**: Use predefined, typed tools (`CivicTools`) to retrieve specific records.
* **Hallucination Prevention**: If the context does not contain the answer, the LLM must return `DATA_NOT_AVAILABLE`.

---

## 9. Data Requirements
* Vector embeddings of representative biographies, project descriptions, and audit reports stored in the `pgvector` database.
* Source metadata and storage paths from the `sources` registry table.

---

## 10. Backend Requirements
* **Prompt Builder**: Formats the prompt template with system instructions, retrieved context, and the user query.
* **Strict Constraints**: The LLM is restricted from:
  * Executing arbitrary SQL statements.
  * Inventing statistics or resolving source conflicts.
  * Performing authoritative financial calculations (these are handled in Python/SQL).

---

## 11. API Requirements
* `POST /api/v1/chat/`: Process questions and return grounded answers with citations.
* `GET /api/v1/chat/history`: Retrieve past chat logs.

---

## 12. Frontend Requirements
* Chat interface with streaming responses and rendering blocks for citations, charts, tables, and maps.
* Diagnostic cards showing the TraceNest `X-Request-ID` for debugging.

---

## 13. Responsive Requirements
* **Mobile**: Single-pane chat view. Citations collapse into a drawer interface.
* **Desktop**: Split-screen showing the chat pane on the left and interactive maps/documents on the right.

---

## 14. Provenance Requirements
Every claim made by the LLM must contain a citation reference mapping back to a verified record in the `sources` registry.

---

## 15. Security Requirements
* **Prompt Injection Defenses**: The backend sanitizes inputs and validates instructions to prevent prompt injection exploits.
* **Model Fallbacks**: Configured with alternative model endpoints to ensure availability.

---

## 16. Error Handling
* **Missing Context**: If no relevant database context is found, the API returns a `DATA_NOT_AVAILABLE` response.
* **LLM Timeouts**: If the inference API times out, the backend fails over to a secondary model endpoint.

---

## 17. Data Quality
The RAG pipeline retrieves confidence scores for context matches, filtering out low-relevance results to ensure answer accuracy.

---

## 18. Performance
* Vector database queries are optimized to keep retrieval latency under 30ms.
* API responses are streamed to reduce perceived latency for users.

---

## 19. Testing
Unit tests verify that the RAG pipeline returns `DATA_NOT_AVAILABLE` when asked questions outside the database context.

---

## 20. Acceptance Criteria
* The LLM only answers using the provided context.
* All claims include citations.
* The LLM cannot execute arbitrary SQL.

---

## 21. Limitations
* Semantic search queries can return irrelevant context for terms with multiple meanings.
* Processing handwritten tables or low-quality OCR text can lead to incomplete context.

---

## 22. Future Work
* Integrating multilingual retrieval models to support regional languages.
* Supporting automated chart generation from retrieved data tables.
